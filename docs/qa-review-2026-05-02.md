## Feature area 1 — Soma extraction overhaul

### Critical

**1.1 `deconv` array misaligned with all other ROI-axis arrays in `ca.h5`.**
Location: `src/hm2p/calcium/run.py:267`.
`F`, `Fneu`, `F_raw`, `Fneu_raw`, `F_corr`, `F0_rolling`, `F0_percentile`,
`dff`, `dff_percentile`, `event_masks`, `noise_probs`, `roi_types`,
`roi_qc/*`, and `roi_qc/p_*` are all written with shape `(n_rois_all,
n_frames)` (the comment on line 146-150 makes this explicit).
`deconv = spks_all[cell_mask]` and `deconv_norm` are filtered to
`iscell == True` only, so they have a different ROI axis length.
Any consumer that indexes `deconv[i]` together with `dff[i]` will read
mismatched ROIs and silently produce wrong scientific results.
Fix: `deconv = spks_all` (no `cell_mask` filter). Apply the iscell filter
once at display-time alongside the ROI-type filter, exactly as is done for
the other arrays.

**1.2 ROI-type encoding loses the artefact distinction.**
Location: `src/hm2p/calcium/run.py:206-209, 323-325`.
After classification, the code maps `if not cell_mask[i] or roi_types[i] ==
"artefact": roi_types[i] = "non-cell"`, then encodes
`type_map = {"soma": 0, "dend": 1, "non-cell": 2}`. CLAUDE.md spec is
`soma=0, dendrite=1, artefact=2`. The current encoding silently merges
"artefact" (a physical artefact ROI) with "iscell=False" (a Suite2p-rejected
ROI that may still be a legitimate dendrite). Downstream analyses that
filter on artefact-vs-non-cell can no longer make that distinction.
Fix: keep `artefact=2` per spec; introduce a separate
`iscell` (or `suite2p_accepted`) bool array if "Suite2p-rejected" needs to
be queryable. Update `roi_types` in `ca.h5` schema accordingly.

**1.3 `RuleBasedClassifier` argmax does NOT match legacy when activity features are present.**
Location: `src/hm2p/extraction/soma_classifier.py:223-263`,
`src/hm2p/extraction/soma_features.py:295-310`,
`src/hm2p/calcium/run.py:185-198`.
The module docstring (lines 12-14) and the test class
`TestArgmaxMatchesLegacy` claim "switching to this classifier therefore
cannot change the soma/dend/artefact label of any existing ROI." That claim
holds only when activity features (`autocorr_halfwidth_s`, `fneu_corr`)
are NaN. The production path in `calcium/run.py` always calls
`extract_soma_features()` which fills these features with finite values;
they then enter `_or_combine(p_dend_shape, p_dend_ac, p_dend_fc)`. A clear
soma by shape (radius=5, compact=0.5, aspect=1) with autocorr_halfwidth=2 s
yields `p_dend_ac ≈ 0.98` (sigmoid of (2−1)/0.25 = 4), `p_dend ≈ 0.98`,
`p_soma ≈ 0.02` — argmax = `dend`, where legacy would say `soma`.
This is not "no relabelling": it is a new classifier that *will* relabel
ROIs in production. The regression test only uses shape features (test file
lines 124-127, 196-217 explicitly say so). Either:
(a) drop the activity contributions in production until a curated-label
classifier is trained, or
(b) update the docstring/contract to say the rule-based classifier may
relabel ROIs and provide a session-level diff report so the user sees the
change.

### Major

**1.4 `compute_dff` hard clip caps physiological signal.**
Location: `src/hm2p/calcium/dff.py:148-149`.
`np.clip(dff, -1.0, 20.0)` silently saturates dF/F at 2000 %. For GCaMP6s
this is rarely hit, but for GCaMP8 high-activity bursts can. More importantly
the lower clip at -1.0 means F0 over-estimation (e.g. when F0_percentile is
biased high) silently flattens negative dF/F into a -100 % wall, which then
masquerades as "active" at the 3·MAD threshold used elsewhere. Either
remove the clip and document that F0 is expected to be a proper lower
envelope, or report `n_clipped` per ROI in attrs so the user knows when it
fires. At minimum log a warning when more than X % of dF/F samples are at
the saturation boundary.

**1.5 `f0_floor` in `compute_dff` uses a 10 %-of-median floor.**
Location: `src/hm2p/calcium/dff.py:144-146`.
`f0_floor = np.maximum(f0_median * 0.1, 1.0)` — for an ROI whose median F0
is 100, the floor is 10. After neuropil subtraction, raw F can drop below
the median F0 by more than 90 %, in which case the dF/F denominator is
clipped to a value far below the local F0. This biases dF/F toward zero in
exactly the windows where F0 is most uncertain (post-bleaching tails,
edges). The choice of 10 % is undocumented and uncited. Either cite a
source or remove the floor and rely on F0 being non-negative by
construction.

**1.6 `estimate_neuropil_coefficient` regresses through the origin in the F-domain.**
Location: `src/hm2p/calcium/neuropil.py:138-155`.
The slope estimator is `α = Σ(F·Fneu) / Σ(Fneu²)` over the bottom-20 %-F
mask, with no intercept. F has a baseline DC offset (resting fluorescence)
that is independent of Fneu. With no intercept, the OLS slope is biased
upward whenever the mean of F is large relative to the mean of Fneu in the
selected window — exactly the case for a sparsely-firing soma with bright
baseline. Dipoppa et al. 2018 fit the *lower envelope* of the F vs Fneu
scatter (a quantile regression), not OLS through the origin on a
percentile-thresholded subset. Either:
(a) subtract the per-ROI mean from both F and Fneu before regressing
(equivalent to fitting with intercept), or
(b) implement the documented Dipoppa lower-envelope quantile regression.
Update the docstring once the implementation matches the citation.

**1.7 `compute_baseline_percentile` propagates NaN with `np.percentile` (not `np.nanpercentile`).**
Location: `src/hm2p/calcium/dff.py:123`.
`np.percentile(F64[:, lo:hi], percentile, axis=1)` with any NaN in the
window returns NaN. Suite2p-rejected frames or motion-correction NaNs in F
will cascade into F0 and from there into dff (NaN propagates through
`compute_dff`). The rolling-min/max baseline path silently masks NaN via
the filter implementation (varies by scipy version), so the two methods
have different NaN behaviour. Either explicitly drop NaN before the
percentile (`np.nanpercentile`) or document that all callers must
pre-fill NaN.

**1.8 `fps_from_timestamps` uses biased estimator.**
Location: `src/hm2p/extraction/run_suite2p.py:123`.
`fps = float(np.mean(1.0 / np.diff(frame_times)))` — by Jensen's
inequality, mean-of-reciprocals is biased high relative to
`1/mean(diff)`. The same module elsewhere (`calcium/run.py:217`) uses
`1.0 / np.median(np.diff(frame_times))` which is correct. The Suite2p
`fs` parameter and the calcium pipeline `fps` are now inconsistent
between the two estimators — the difference is small (sub-Hz at 9.6 Hz)
but compounds across `tau`, baseline windows, and CASCADE model
selection. Use `1.0 / np.median(np.diff(frame_times))` everywhere.

**1.9 `n_tiff_frames` is sourced from `dff.shape[1]`, not from Suite2p `ops.npy`.**
Location: `src/hm2p/sync/align.py:179-183`.
The design doc (`docs/sync-pipeline-design.md` line 234) says
`n_tiff_frames` is "From Suite2p ops.npy if available; -1 if not". The
implementation reads `int(ca["dff"].shape[1])` which is the count of
imaging frames *after* Suite2p extraction (Suite2p's `nframes` from
`ops.npy` after any frame trimming). Comparing `img_n_pulses` to
post-extraction frame count cannot detect the case where Suite2p dropped
or trimmed frames — `pulse_count_diff` will be silently clean even when
Suite2p quietly lost frames. The off-by-one heuristic at
`build_scalars` line 845 also becomes meaningless under this sourcing.
Fix: read the original frame count from `ops['nframes_init']` or from
TIFF metadata before any trimming; pass it through Stage 4 → Stage 5.

**1.10 `bad_imaging_frames` length mismatch silently truncated/padded.**
Location: `src/hm2p/calcium/run.py:351-358`.
The `if len(bad_imaging_frames) >= n_dff: ... else: pad with False`
policy hides a real Suite2p mismatch. If Suite2p's `ops['badframes']`
indexes frames beyond `dff.shape[1]`, that itself indicates a frame-count
inconsistency — silently truncating loses the signal. Logging a warning
when truncation/padding actually fires is the minimum; raising on a
sufficiently-large mismatch is safer.

**1.11 `_quick_dff` floor logic is dead-equivalent.**
Location: `src/hm2p/extraction/soma_features.py:117-119`.
```
f0_floor = np.maximum(f0, 1.0)
f0_safe = np.where(f0 > f0_floor, f0, f0_floor)
```
`f0_floor >= f0` always, so `f0 > f0_floor` is always False, so
`f0_safe = f0_floor = max(f0, 1.0)`. The expression is logically the
same as `np.maximum(f0, 1.0)`. Not a bug, but the convoluted form
suggests the author intended a different semantics (perhaps a per-ROI
median floor like `compute_dff`). Reconcile or simplify.

### Minor

**1.12 CASCADE 9.6 Hz vs 10 Hz model: warning silenced, no audit trail.**
Location: `src/hm2p/calcium/spikes.py:33,86-96`.
`_FPS_MISMATCH_THRESHOLD_HZ = 1.5`; at 9.6 Hz session vs 10 Hz model the
delta is 0.4 Hz — silent. CASCADE itself is sensitive to fps mismatch in
the < 0.5 Hz range. The threshold of 1.5 Hz is generous; consider 0.5 Hz
plus an info-level log at every invocation reporting the actual delta.
Per Rupprecht et al. 2021, downstream rate biases scale roughly linearly
with the fps ratio.

**1.13 `_parse_model_fps` regex matches `\d+(\.\d+)?Hz` without a leading word boundary.**
Location: `src/hm2p/calcium/spikes.py:47`.
`Global_EXC_10Hz_smoothing200ms` parses correctly to 10.0. But
`Global_EXC_v100Hz_smoothing` would also parse to 100.0. Edge-case;
unlikely to bite given current model naming. A `(?<![A-Za-z0-9])`
lookbehind guards against future surprises.

## Feature area 2 — Sync pipeline diagnostics

### Critical

**2.1 `dlc_champion_id` not propagated into FAILED_* sync.h5 stubs.**
Location: `src/hm2p/sync/align.py:91-134, 319-321`.
For sessions classified `FAILED_*`, `_write_stub` is called with only
`session_id`, `status`, `warnings`, `failures`, and `diag_attrs`. The
champion-id contract in CLAUDE.md ("Every derivative produced from DLC
pose data ... records a `dlc_champion_id` attribute that identifies which
model produced it") is silently violated for the failed-sync case. The
report aggregator (`report.py:114`) tolerates the absence with `""` —
which means a stale failed session is indistinguishable from a current
failed session in the parquet, and the `is_session_current` check on the
frontend cannot decide whether to keep a stale-but-failed session
visible. Fix: read `dlc_champion_id` from `kinematics.h5` attrs early
(before classification) and pass it into `_write_stub`.

### Major

**2.2 `n_tiff_frames` taken from `dff.shape[1]`, not Suite2p `ops['nframes']`.**
(Same root cause as 1.9.) The frame-count cross-check
(`build_scalars` line 843-846) treats `n_tiff_frames` as the
pre-extraction TIFF frame count, but Stage 5 hands it the
post-extraction count. The off-by-one heuristic and the
`frame_count_minor_mismatch` warning therefore measure
`img_n_pulses − n_imaging_frames`, not `img_n_pulses − n_tiff_frames`.
The two are not the same when Suite2p drops frames during registration.
This makes one of the seven sync tiers and three of the warnings
misleading.

**2.3 `bad_imaging_frames` and `bad_behav` truncated silently in align.py.**
Location: `src/hm2p/sync/align.py:373-380`.
`bad_imaging_t = np.asarray(bad_imaging[:n_frames], dtype=bool)` and
similarly for `bad_behav`. Both are sliced to `[:n_frames]` without any
length check or warning. If either is shorter than `n_frames`, the
`np.asarray(..., dtype=bool)` doesn't error — but the resulting
`bad_frames` mask will be too short, and the `|` in
`bad_imaging_t | bad_behav_t` will broadcast or shape-error depending on
whether both are short. Add an explicit length check and either pad to
`n_frames` (and warn) or fail loudly.

**2.4 `_duty_cycle` ignores edges with `t < 0` rather than processing them.**
Location: `src/hm2p/sync/diagnostics.py:421-422`.
`if t < 0.0: continue` skips negative-time edges entirely — but each
edge represents a state flip. Skipping the edge keeps the prior state
through to the next non-negative edge, which double-counts time in the
old state. Real DAQ pulse times should be ≥ 0 by construction, but
defensive code that "skips" edges should also skip the state flip *and*
the t_prev advance. Either drop the t<0 check (let walker integrate
zero-duration negative-time intervals harmlessly) or remove t<0 edges
upstream.

**2.5 `n_isi_outliers` over-reports on perfectly uniform synthetic trains.**
Location: `src/hm2p/sync/diagnostics.py:302-307`.
When MAD == 0, the threshold becomes
`tol = 1e-9 * max(median_isi_s, 1e-9)`. For a 100 Hz camera
(median_isi_s ≈ 0.01), `tol ≈ 1e-11` — well below floating-point ISI
noise from `np.diff` of float64 timestamps. A perfectly clean test
fixture will report many "outliers". This isn't surfaced as a warning
(the code path that flags `duplicate_pulses_*` uses a different
predicate), so the parquet reports a noisy `n_isi_outliers` that
QC dashboards may misinterpret. Either widen `tol` (e.g.
`tol = 1e-6 * median_isi_s`) or document the behaviour.

### Minor

**2.6 Median-ISI nominal in `drift_slope` has a circular-reference edge case.**
Location: `src/hm2p/sync/diagnostics.py:222-224`.
When `fps_nominal` is None the reference ISI is the empirical median.
Drift slope is then computed as deviation of regression slope from that
empirical median — but the regression slope itself is a smoothed median
in expectation. The two will be near-equal when the true drift is small,
masking real drift in the ppm range. Pass `fps_nominal` explicitly from
the caller wherever possible (the call sites already do — this is fine
in practice, but the docstring should call out that None is for tests
only).

### Verified Correct

- The seven-tier first-match-wins classifier in
  `diagnostics.py:498-661` has no overlap between failure tiers and
  warnings; tier ordering is asserted by `tests/sync/TEST_PLAN.md` §3.2
  and checked by parametrised tests.
- Drift estimation is regression-based with R² and ppm reporting; it is
  robust to outliers via the median-based reference. (The QA brief
  asked specifically about robust drift — slope is OLS, but the
  reference is median, which is the methodologically defensible
  choice.)
- `infer_light_polarity_ok` uses non-parametric duty-cycle bounds,
  not Gaussian assumptions on the light pulse train.
- `code_message` lookup table has one entry per code and is the only
  source of truth for warning/failure messages.
- `is_sync_clean` and the `FAILED_*` prefix contract are consistent
  between `frontend/data.py:1712-1749` and
  `src/hm2p/analysis/run.py:check_sync_status`.
- `build_report` reads only root attrs (no datasets); a corrupted dff
  array does not block the aggregator. Test
  `test_corrupt_dff_does_not_block_aggregator` exists.
- The 18 failure modes in `tests/sync/TEST_PLAN.md` are each mapped to
  a specific test; coverage matrix is complete.
- `evaluate_gate` in `pose/finetune.py` is independent — sync is not
  contaminated by SA fine-tune statistics.
- Pandera/JSON validators for `sync_diag/` columns match
  `SYNC_DIAG_INT_KEYS` / `SYNC_DIAG_FLOAT_KEYS` exactly.

### Ship-readiness verdict — sync pipeline diagnostics

**needs-fixes-before-merge.** 2.1 (champion-id on stubs) and 2.2
(`n_tiff_frames` source) are real contract / methodology violations.
2.3 is a defensive-code bug that will surface as a confusing crash
rather than a silent-wrong-result, but it's still a bug. 2.4 / 2.5 are
edge cases that should not block merge once 2.1-2.3 are fixed.

## Feature area 3 — SA fine-tune

### Critical

(none.)

### Major

**3.1 `evaluate_gate` no-regression "within band" test combines magnitude and significance with `<` boundaries.**
Location: `src/hm2p/pose/finetune.py:919-938`.
The boundary semantics are subtle: `within_band = pct_change_median >
-other_keypoint_max_regression_pct` (strict `>`, so exactly -10 % fails).
Then "inside band" but-significant fail uses
`p_value_wilcoxon < other_keypoint_regression_p_max` (strict `<`, so
exactly p=0.05 does *not* fail). The two boundary semantics are
inconsistent: the no-regression test fails strictly, but the
in-band-significant test fails strictly-below. Tests verify both
behaviours but the design rationale is opaque. If the user's intent is
"strict everywhere on the side of failing the candidate", the in-band
test should be `<=` to be symmetric.

**3.2 `bootstrap_median_ci` is empirical percentile, not BCa, but documentation says "no parametric assumption".**
Location: `src/hm2p/pose/finetune.py:227-281`.
Per the plan v2 §4.5 (cited in the docstring), percentile method is the
chosen variant. The docstring is correct in saying "no parametric
assumption"; what it doesn't say is that percentile-CI is biased for
skewed distributions, particularly when the bootstrap distribution of
the median is not centred on the sample median (small-n right-skewed
keypoint errors are a typical case). For the v2 plan §4.5 the choice is
documented, so this is a *documentation* issue: surface the bias caveat
in the methods text on the tracking-quality page so reviewers understand
the trade-off vs BCa.

**3.3 `evaluate_promotion_gate` HD panel always uses `alternative="greater"` for HD Wilcoxon.**
Location: `src/hm2p/pose/finetune.py:1023-1025`.
Wilcoxon `(hd_b_v, hd_c_v, alternative="greater")` tests
H1: `hd_b > hd_c` (candidate better than baseline). HD is descriptive
only per the plan, so the p-value isn't gating; but reporting a
one-sided p-value with no explanation invites reviewer pushback. Either
report two-sided HD p-value (descriptive, makes no sign assumption) or
document explicitly in the methods expander that the HD test is
one-sided to match the keypoint tests.

### Minor

**3.4 `paired_wilcoxon_per_keypoint` `min_pairs` is checked on non-zero diff count.**
Location: `src/hm2p/pose/finetune.py:148-149`.
The threshold is `n_nonzero < min_pairs` where `n_nonzero` is the count
after dropping zero-diff pairs. With `zero_method="wilcox"`, scipy also
drops zero-diff pairs internally. So a column with 9 non-zero pairs but
100 total finite pairs returns NaN — which the gate then treats as a
failure. That's correct. But: a column with `min_pairs - 1 = 9`
non-zero pairs is reported "insufficient data" while a column with
exactly 10 runs the test on an effective n=10, which is statistically
weak. Consider raising `DEFAULT_MIN_PAIRS` to 20 or 30 — Wilcoxon at
n=10 has very low power against realistic effect sizes.

**3.5 `verdict_from_json` does not verify gate-config consistency.**
Location: `src/hm2p/pose/finetune.py:698-709`.
The deserialiser pulls gate fields with `.get(..., default)` per field.
A verdict whose JSON has `gate.alpha = 0.10` (loosened from 6.25e-3)
will round-trip without complaint. The schema fixture
`tests/pose/fixtures/verdict.schema.json` does not pin the alpha value
either. If a verdict is ever reissued with a different gate, the
overall_pass and fail_reasons fields are no longer interpretable
without reading the gate sub-object — and downstream tooling
(`tracking_quality_page.py`) assumes the canonical thresholds. Either
pin the gate config in the JSON-Schema or add an explicit
`assert verdict.gate == GateConfig()` at the consumer side.

### Verified Correct

- All hypothesis tests are non-parametric: paired Wilcoxon
  (`zero_method="wilcox"`), rank-biserial, Spearman (none in the gate,
  but `qc.compute_fneu_dff_corr` uses Spearman), bootstrap percentile.
  No t-tests, no Pearson, no ANOVA in the new code under
  `pose/finetune.py`, `compare_models.py`, or
  `tests/pose/`.
- Bonferroni correction is `alpha / n_tests` via `bonferroni_alpha`,
  and the gate uses `alpha = 0.05 / 8 = 6.25e-3`. Tested at boundary.
- Gate boundary tests cover exactly the predicates the user asked for:
  `r = 0.30` passes (`>=`), `r = 0.29` fails; `p < alpha` with `p =
  alpha` fails; `pct_change = 0.30` exactly passes for nose; `pct_change
  = -0.10` exactly fails on no-regression (strict `>`). All present and
  asserting correctly.
- Verdict round-trip preserves NaN / infinities through `allow_nan=True`
  in `json.dumps`. `KeypointVerdict` and `Verdict` dataclasses are frozen
  and hashable.
- `schema_version` enforcement: forward-incompatible (`"2.0"`),
  zero (`"0.0"`), and missing all raise `ValueError` per
  `verdict_from_json`. Schema fixture has `"const": "1.0"`.
- `circular_abs_error` correctly wraps via `arctan2(sin, cos)` to
  `[0, π]` — circular distance, not linear.
- `hd_from_ear_vector` matches the existing `kinematics.compute`
  convention (forward perpendicular, image y-axis down).
- `probe_sa_detector_bbox_rate` is pure-function, takes a list of
  booleans, threshold-defaults to 0.90 per design §6.
- `evaluate_promotion_gate` does NOT factor HD into `overall_pass` —
  HD is descriptive only as documented.
- `--sa-finetune` passthrough in `launch_dlc_finetune_ec2.py` and
  `run_dlc_retrain.py` is unit-tested with mocked DLC calls.
- The methods expander on the tracking-quality page cites
  Ye et al. 2024 (SuperAnimal), Kerby 2014 (rank-biserial), and the
  bootstrap percentile method.

### Ship-readiness verdict — SA fine-tune

**ready-as-is** with the caveat that 3.5 (gate-config pinning) is worth
addressing before this is the canonical promotion gate for production
DLC retrains, and 3.3 (HD one-sided p-value) deserves a one-line
methods-expander note. 3.1 / 3.2 / 3.4 are reviewer-defence concerns
not bugs.
